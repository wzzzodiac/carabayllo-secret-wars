==================================================
1. PROJECT IDEA / DESIGN PHILOSOPHY
==================================================
Orbital Artillery is a browser/desktop multiplayer artillery game inspired by Gunbound/Wild Ones.

Goals:
- 2–8 players.
- Team and Survival.
- Private room codes.
- Server-authoritative state.
- Destructible terrain.
- Turn-based combat.
- Wind, angle and power.
- Vehicles with movement and jumps.
- Pickups and special weapons.
- Browser-first deployment.
- GitHub Pages frontend.
- Google Cloud Run backend.
- Small/private-use architecture with target cost near €0/month at low activity.

Design principles:
- Server owns authoritative gameplay state.
- Client renders and sends player intent.
- Gameplay should be readable, chaotic and fun without opaque mechanics.
- Add features in small testable blocks.
- Manual QA is tracked separately in versioned TODO files.
- Reusable debugging procedure is COBY_GITHUB_DEBUGGING.
- Desktop/web is the target. Mobile/touch gameplay is out of scope.

==================================================
Frontend:
- GitHub Pages.
- HTML/CSS/JavaScript ES modules.
- Canvas 2D.
- Socket.IO client loaded dynamically.
- Backend connection begins on CREATE/JOIN; merely opening the page should not intentionally wake Cloud Run.

Backend:
- Node.js + Socket.IO.
- Region us-east1.
- Public unauthenticated service.
- Port 8080.
- In-memory rooms; no database.
- Instance restart loses active rooms; accepted for MVP.
- Intended Cloud Run configuration: min instances 0, max instances 1, ingress all.
- CORS limited to configured GitHub Pages origin.

Current/default server limits:
- max rooms 20
- max players 8
- max concurrent sockets 64
- connection attempts 20/min/IP
- packets 30/s/socket
- idle sockets outside countdown/started matches: 30 min
- countdown/started sockets protected from idle timeout

Deployment workflow:
1. Commit to main.
2. GitHub-linked Cloud Build triggers.
3. Cloud Run deploys automatically.
Manual revision deployment is normally avoided because source-trigger deployments are authoritative.
Never assume backend deployment completed without verifying it.

Cost philosophy:
- backend sleeps when unused
- frontend does not auto-connect on page load
- min instances remains 0
- expected max instances 1
- budget alert around €5/month
- thresholds 50/90/100/150%
- budget alert is NOT a hard cap

==================================================
6. TURN SYSTEM / STARTER / WIND
==================================================
Turn:
- 40 s.

Wind:
- generated by server each turn
- direction/strength shown in HUD
- affects projectile acceleration

Turn order:
- Survival circular
- Team alternates A/B where possible

Starter weighting — intentional design:
- host is intentionally less favored
- 2 players: host 40%, other 60%
- 3 players: host 20%, others 40/40
- larger rooms follow current weighted formula
Do not change unless Walter explicitly changes design.

Physical spawn order:
- randomized independently from join order.

Normal projectile rule:
- shot resolves and ends turn.
Exception:
- successful explosion pickup can preserve shooter turn.
- shooter resumes with approximately pre-shot remaining time.
- minimum restored/resume time 1 s.
- no pickup => normal turn advance.

11. AFK SKIP VOTE — Phase 6B.1
==================================================
Purpose: prevent inactive players from stalling.

Rules:
- 40 s turn
- opens at 20 s remaining
- F1 vote toggle
- living non-active players only
- active player cannot vote own skip
- one vote per voter
- strict majority floor(eligible/2)+1

Examples:
- 2 living total: 1/1
- 3 total: 2/2
- 4 total: 2/3
- 5 total: 3/4

On pass:
- current turn skips immediately
- HUD can show TURN SKIPPED // AFK VOTE

Anti-abuse:
- valid active-player action clears votes
- rejected/invalid action does not
- valid actions include accepted movement/jump/aim/power/selection/fire/Shield/Heal/etc.

Disconnect/race handling:
- eligible voters recalculate
- existing votes can become sufficient after disconnect
- active valid action can cancel pending skip race and restore normal deadline semantics
- no double advance

Browser:
- F1 reserved during active match to avoid Help interference
