CONFIRMED ISSUE 1 — INITIAL PLAYER RANDOMIZATION BIAS
==================================================
Severity: LOW/MEDIUM gameplay fairness issue.
File: orbital-artillery-server/rooms.js
Function: chooseInitialPlayerId(room, order)

Current algorithm calculates:
- hostWeight = 0.4 / (order.length - 1)
- otherWeight = (1 - hostWeight) / (order.length - 1)

This is not a uniform random choice.
Examples:
- 2 players: host 40%, other 60%.
- 3 players: host 20%, each other 40%.
- 4 players: host ~13.3%, each other ~28.9%.

Unless an intentional anti-host starting handicap was explicitly designed, this contradicts the natural expectation of "randomize match starts".

Recommended fix before/with next gameplay pass:
Choose one ID uniformly from turnOrder, e.g. random index, unless a deliberate weighted starter rule is desired.

Manual decision needed from Walter:
- Should every player have exactly equal chance to start?
Recommended answer: YES.

==================================================
CONFIRMED ISSUE 2 — AIR STRIKE VOID DEATH HAS NO FALL ANIMATION
==================================================
Severity: MEDIUM visual/gameplay presentation issue.
File: orbital-artillery-server/phase6c.js
Function: settleAfterAirStrike(room, now)

Current void branch after Air Strike terrain deformation does approximately:
- player.hp = 0
- player.alive = false
- player.motion = null

Therefore if Air Strike removes terrain beneath a player deeply enough to produce void, the server can instantly kill the player without a fall motion.

This differs from the normal projectile/void paths in rooms.js, which create fall/void motion and delay result resolution for presentation.

Expected symptom:
A tank may disappear/die instantly after an Air Strike crater instead of visibly falling into the void.

Recommended fix:
Reuse the normal void-fall semantics or create an Air Strike equivalent:
- set target below world,
- create fall motion,
- delay match result until fall animation finishes,
- keep camera following the falling player where appropriate.

This should receive a regression test.

RISK 1 — AIR STRIKE MULTI-SHELL FALL MOTION OVERWRITE
==================================================
Status: POTENTIAL / MANUAL + CODE REVIEW NEEDED.

settleAfterAirStrike() is called after each applied shell.
A player moved downward by an early shell may receive a new fall motion from a later shell before the first visual fall finishes.

Possible symptom:
- snapping,
- fall animation restarting,
- odd vertical interpolation during barrage.

Not proven broken from static inspection.
Add to manual test list.

==================================================
RISK 2 — TERRAIN IMPLEMENTATION DUPLICATION
==================================================
Status: TECHNICAL DEBT, not a confirmed current bug.

Terrain surface/base shape logic is duplicated across:
- server rooms.js
- server phase6a.js
- server phase6c.js
- frontend renderer.js

Currently the formulas inspected appear aligned, but this is fragile.
A future terrain adjustment could change one copy and silently desynchronize:
- server collision,
- pickup placement,
- Air Strike shell placement,
- client rendering.

Recommended future refactor:
Centralize/share terrain definitions and surface evaluation where practical.
Do not block Phase 6D solely for this unless terrain changes are planned.
